# 03 订单生命周期与状态业务含义

## 订单的一生:状态流转全图

下单(101)→ 付款(201)→ 发货(301)→ 确认收货(401 用户/402 超时/403 管理员)→ 评价完成。异常支线:未付款取消(101→102 用户取消 / 103 超时取消 / 104 管理员取消);付款后退款(201/301→202 申请退款→203 已退款)。状态码存在 `litemall_order.order_status`,百位数字代表环节:1xx 交易开始前,2xx 已付款/退款,3xx 物流,4xx 收货完成。

## 101 未付款(待支付)

用户已提交订单但未支付。订单生成时锁定优惠券与库存;超过 30 分钟未支付会被定时任务自动取消(转 103)。查询场景:"有多少弃单/未支付订单"= 当前 status=101;历史弃单率 = (102+103) ÷ 全部订单。资金未到账,不计入销售额。

## 102 / 103 / 104 已取消(用户取消/超时取消/管理员取消)

102 = 用户主动取消;103 = 超时未付系统自动取消(本库约 1,977 单);104 = 管理员强制取消。取消订单不产生交易,不进销售额;但它们与 101 一起构成"流失分析":若大量 103,说明支付环节有阻力。

## 201 已付款(待发货)

钱已到账,等待商家发货。**"待发货订单" = status=201**,是商家每天要处理的队列(本库约 1,289 单在途)。从 201 起订单计入销售额;201 上可发起退款申请(→202)。

## 202 申请退款中(售后进行时)

用户在发货前/后申请退款,订单挂起等待商家审核。与售后表联动:aftersale.status=1(用户已申请)。查询"待处理的退款申请" = status=202,是客服工作队列。

## 203 已退款(交易关闭)

退款完成,资金按 refund_type(微信退款/支付宝退款/原路退回)退回 refund_amount(可能小于实付=部分退款)。订单关闭(end_time),不计入销售额;计入退款率分子。本库约 4,267 单,主要原因是"七天无理由""不想要了"。

## 301 已发货(待收货)

商家交快递(ship_channel 五家:顺丰/中通/圆通/韵达/京东),ship_sn 为运单号。"在途订单" = status=301。发货时长 = ship_time − pay_time,是履约 KPI。

## 401 / 402 / 403 已收货(交易完成的三种方式)

401 = 用户手动确认收货;402 = 发货后超期系统自动确认(本库最多,约 24,698 单);403 = 管理员代确认。三者业务上都代表**交易完成**,统计"已完成订单"时合并 `status IN (401,402,403)`。收货后 `comments>0` 表示还有商品待评价,评价写入 comment 表后递减。

## 订单各时间字段的业务含义与选用

add_time 下单 / pay_time 支付 / ship_time 发货 / confirm_time 收货 / refund_time 退款完成 / end_time 订单关闭 / update_time 最后变更。**默认统计维度用 add_time**(下单口径,符合"今年的订单"直觉);用户问"支付金额按月"等明确环节时换对应字段。时效指标必须用相邻两字段之差,且这些字段在对应状态之前为 NULL,SQL 需判空。

## aftersale_status 与 order_status 的联动

订单表上的 `aftersale_status`(0可申请,1已申请,2审核通过,3退款成功,4拒绝,5取消)是售后进度的冗余快照,与售后表 status 同步。查售后明细一律用 litemall_aftersale;order_status=202/203 是订单视角的结果。两者不要混在同一个条件里重复过滤。
