# 00 业务背景与数据边界

## 这是一家什么店

`litemall` 库是一家**自营家居百货微信小程序电商**的业务库(类似网易严选模式):平台自己采购商品、加价零售。商品集中在居家(床上用品、被子、四件套等,170 款)、餐厨、饮食、服装、婴童、洗护等 9 个一级类目,共 239 款商品、244 个 SKU 货品。用户在小程序下单,微信支付,商家通过顺丰/中通/圆通/韵达/京东物流发货。

## 这家店怎么赚钱(盈利模式)

自营电商的盈利模式是**进销差价**:利润 = 销售额 − 商品采购成本 − 物流成本 − 优惠券让利 − 平台/运营费用。零售价(`retail_price`,可对标专柜价 `counter_price` 体现让利感)高于进货价,卖出即产生毛利。

## ⚠ 数据边界:没有成本,算不出利润

本库**没有采购成本、进货价、运营费用、工资房租等任何成本费用字段**。因此:

- 用户问"**赚了多少钱 / 利润 / 毛利 / 盈利**"→ **无法直接回答利润**。正确做法:说明库中没有成本数据,改用"销售额(实付口径)"回答,例如"无法计算利润(库中无成本数据),经营期实付销售额为 XX 元";若用户坚持要看"接近利润"的数,可用 `SUM(actual_price) - SUM(refund_amount)`(净销售回款)并说明这只是回款不是利润。
- 用户问"**转化率 / 流量 / UV / 访客**"→ 库中没有浏览、加购未买、搜索流量等行为数据(无 footprints/cart 行为留存),无法计算转化漏斗,应声明边界。
- 用户问"**采购 / 供应商 / 进货**"→ 库中无供应商与采购单数据,只有销售侧。

## 资金视角:一笔钱怎么流

用户下单未付款(无资金流)→ 支付成功,平台收到 `actual_price` 元 → 使用优惠券时商家让利 `coupon_price`,积分抵扣 `integral_price`,运费 `freight_price` 由用户承担 → 若退货退款,按 `refund_amount` 退回(可能部分退款)→ **商家实际留存回款 = SUM(actual_price) − SUM(refund_amount)**(不含成本,不是利润)。

## 分析框架:人-货-场

电商分析的标准框架,用户问题大多可归入其中一类:

- **人(用户)**:注册量、下单用户数、复购率、客单价、新客/老客、会员等级分布、用户消费排行 → 涉及 litemall_user、litemall_order
- **货(商品)**:销量榜、销售额榜、动销率、库存、品类结构、价格带 → 涉及 litemall_goods、litemall_goods_product、litemall_order_goods、litemall_category、litemall_brand
- **场(交易与营销)**:GMV 趋势、大促效果、优惠券核销、退款率、物流时效 → 涉及 litemall_order、litemall_coupon(_user)、litemall_aftersale
